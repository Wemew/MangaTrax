## 2. New blocking issues (introduced by v0.2)

| # | Issue | Why it blocks | Concrete fix |
|---|---|---|---|
| **N1** | **Overlay ladder puts the Tasks button above the sheet/palette, and the dialog helper only inerts main/header/footer.** UX-007:89 assigns Tasks z=95 while the sheet is 70, palette is 90 and their backdrops are 60/80 — so on mobile the Tasks button floats on top of the open bottom sheet, and on desktop it sits above the palette; UX-013:147-148 sets `inert` only on `#main-content`, header and footer, so `#global-tasks`, `#toast-container`, `#toast-errors`, `#offline-banner` and the bottom bar remain in the accessibility tree — and Tasks plus the toast controls stay pointer-interactive above the modal backdrop — while an `aria-modal` dialog is open. UX-014 additionally mandates persistent error toasts with a Retry button, which would then be clickable above the modal backdrop but unreachable by the dialog-focused keyboard path. | This is an internal contradiction between two new requirements (modal semantics vs. z-ladder): implemented literally it ships a fixed control above an `aria-modal` dialog and leaves non-dialog body content outside the inert scope (WCAG 2.1 AA 4.1.2/1.3.1 and the spec's own dialog contract). | Reorder the ladder so dialogs are above global chrome (e.g. Tasks 55, bottom bar 40, backdrops 60/80, sheet 70, palette/modals/lightbox 90, toasts 100) **and** make the helper inert/aria-hide every non-dialog body child — `#global-tasks`, `#offline-banner`, bottom bar, and the interactive controls inside `#toast-container`/`#toast-errors` — **without** hiding the live-region containers themselves (a live region left in the accessibility tree is required for announcements; its buttons are set `aria-disabled`/`pointer-events:none` while a dialog is open, or the toast is rendered inside the dialog’s focus scope). Add these rules to UX-013 and UX-007 and an §4 assertion. |
| **N2** | **Discovery tabs are specified as `role="tab"`/`aria-selected` without the rest of the tab pattern.** UX-025:254-255 and UX-017:183-184 only require role/aria-selected; no `role="tablist"`, no `aria-controls`/`role="tabpanel" aria-labelledby`, no roving tabindex, no ArrowLeft/Right/Home/End. | A changed surface that announces itself as a tab set but behaves like plain buttons is an ARIA/AT conformance gap (the same class of issue I blocked for the nav menus in round 1, now fixed there): screen-reader users hear “tab 1 of 2” and expect arrow-key navigation; without tablist/tabpanel the tab↔panel relationship is not programmatically determinable (WCAG 1.3.1/4.1.2 under the spec’s own AA commitment), and if inactive tabs get `tabindex="-1"` they become keyboard-unreachable without arrow keys. | Either (a) implement the full pattern: `role="tablist"` on the container, per-tab `id`+`aria-controls`+`aria-selected`, panels `role="tabpanel" aria-labelledby`, roving tabindex with ArrowLeft/Right/Home/End, keeping the `#discovery`/`#blacklist` hash restore; or (b) keep plain buttons/links with `aria-current="true"` (no tab roles) and state that choice explicitly. Add a source-level assertion in the new suite. |
| **N3** | **New chrome still conveys state by colour only, and the pickup dot has no accessible name.** UX-005:61-62: active bottom tab = `aria-current` + “brand accent” (colour); no non-colour visual cue (weight/indicator/icon fill) is required. UX-004:52-54: the mobile Downloads tab indicator is “a small dot” for active pickups, with no accessible text/`aria-label` and no count exposure on that tab. | WCAG 1.4.1 (AA) — colour must not be the only visual means of conveying the active tab; and the dot conveys a state that is not programmatically determinable for screen-reader users (4.1.2 / 1.1.1), on a newly added primary navigation surface. The spec’s non-negotiable 4 claims AA for changed surfaces. | UX-005: require a non-colour active cue (font-weight change + 2 px top indicator bar or filled-icon variant) in addition to `aria-current="page"` and the accent. UX-004: give the Downloads tab an accessible name that carries the state (`aria-label="Downloads, N manual pickups waiting"` or a visually-hidden span) and mark the decorative dot `aria-hidden="true"`; do the same for the badge on the menu link. |

## 3. Remaining non-blocking notes (no verdict impact; implementation checklist)

1. **A11y scan extension needs 9 pre-existing partial fixes.** §4:323 extends the icon-only scan to `templates/partials/*.html`, but 9 partial buttons currently have `title` only (no `aria-label`): `partials/flat_release_row_chunk.html:179,184,188,193` (download/ignore/unignore/blacklist) and `partials/series_card_chunk.html:261,265` (ignore/unignore) and `partials/series_table_row_chunk.html:4,62,65` (monitor toggle, edit link, blacklist). UX-022 only promises the monitor toggle; Phase 1 must fix all nine or the extended assertion cannot pass. Add them to the UX-022/UX-017 scope explicitly (no design change; scope completeness).
2. **`aria-expanded` sync for the palette trigger.** UX-002:33 puts `aria-expanded="false"` in the markup; UX-010/UX-013 do not say who toggles it. Add “the helper/trigger keeps `aria-expanded` in sync on open/close” to UX-013 (same for the sheet’s two openers, already implied by UX-006).
3. **UX-018 catalogue additions** (currently absent but test-pinned): `id="settings-section-nav"` + `sticky top-20` (`test_ui_polish.py:53-54`), `aria-label="Open navigation menu"` / `closeMobileMenu()` (`:198-199`), `/api/tasks?active=0` / `tasks-panel` / `tasks-active-count` / `tasks-toast` (`test_background_tasks.py:161-165`), `btn-check-feeds`/`icon-feed-check`, `btn-sync-calibre`/`icon-calibre-sync`, `btn-tag-staging`/`icon-staging-tag`, `nav-link-loading`, `link.closest('nav')`, `onclick="toggleMobileMenu()"`.
4. **Ledger accuracy:** G-27 (modal trap/Escape) is marked FIX but only the sheet/palette/lightbox/tag/feeds modals migrate; UX-013 defers the remaining modals. Mark G-27 PARTIAL (migrated set listed) to keep acceptance §5.4 honest.
5. **UX-030 cross-reference:** “blank password = unchanged … listed in §7” — the semantics change is tracked in §4 (new-suite row), not §7; fix the pointer (or add a §7 row).
6. **Responsive-table semantics risk (not blocking):** CSS-only table→card conversion can drop table semantics in some browsers when `display` changes; UX-022’s “hide `<thead>` visually but keep `scope='col'` for AT” is good intent — add “preserve row/cell relationships (avoid `display:flex` on table/tr; verify with a screen reader or keep `role=table/row/cell`)”. Also verify the `data-label` pseudo-content is not double-announced.
7. **`role="tab"` alternative (N2)** is the only structural ARIA change; everything else (menus, dialogs, live regions, aria-busy, safe-area) is now consistent with APG/WCAG intent.
8. **Section-reference governance is inconsistent.** Non-negotiable 3:16 says “pinned literals are preserved unless explicitly listed in **§7**” and calls §7 “the full catalogue”, but §7 is “Deferred (Phase 2)”; the catalogue is UX-018 and the exception matrix is **§4** (acceptance §5.1 correctly says “without a §4 row”). UX-030:307 (“listed in §7”) and UX-013:151 (“listed in §8”) have the same slip. Retarget those three pointers to §4/§7 respectively so implementers do not look in the wrong table before touching a pinned literal.
9. **Visual-language constraint dropped.** v0.1 non-negotiable “visual style stays consistent with the existing dark brand — no light theme, no new accent colours” is absent from v0.2’s non-negotiables (goal line only says “one shared visual language”). Restore it as a constraint on the new surfaces (bottom bar / dot / palette / chips must reuse existing brand+slate/cyan/amber/emerald tokens from `base.html:12-31`) so UX-015’s token table remains the single source of colour.
