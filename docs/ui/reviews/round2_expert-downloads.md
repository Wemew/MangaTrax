## 2. New blocker (round 2)

**N1 — `#global-tasks` sits above every dialog and is not inert, breaking modal modality and the "no overlay overlaps another overlay" acceptance rule.**
The ladder (UX-007) puts the Tasks button/panel at `z:95`, above the generic modal backdrop (`60`) and above palette/lightbox/tag/match/feed dialogs (`90`). The dialog helper (UX-013) sets `inert` only on `#main-content`, header and footer. In the current DOM `#global-tasks` is a **body-level sibling after `</footer>`** (`base.html:594` in the working tree; previously line 390), so it is neither inside an inert region nor hidden — while a tag modal, palette or any dialog is open the Tasks button stays clickable and its panel renders **on top of** the dialog/backdrop. That violates `aria-modal="true"` modality (content outside the dialog must be inert), can overlap the dialog on small screens (320–390 px), and contradicts acceptance §5.2 ("no fixed overlay overlaps primary content or another overlay"). The working-tree partial implementation already reproduces this: `MangaModal.open` inerts only `main-content`/`site-header`/`site-footer` (`base.html:1402-1405`) and CSS keeps `#global-tasks { z-index:95 }` (`base.html:189`).
**Fix (one of, both cheap):** (a) add `#global-tasks` (and any future body-level floating UI) to the `MangaModal` inert/hide set while a dialog is open; and/or (b) state in the ladder that Tasks `z:95` applies only when no dialog is open (otherwise hidden or lowered below the `60` backdrop). Add an acceptance assertion (source check that the inert list includes the tasks node, or that tasks is hidden while `.mt-modal-open` is set).

## 3. Non-blocking notes (no sign-off impact)

- **N2 — G-29 ledger.** §8 marks G-29 **FIX**, but UX-027 deliberately forbids row add/remove, so a torrent that starts while the page is open will not appear until the next page load/action (the audit text's "stale progress/state" symptom is fixed for existing rows). Recommend recording G-29 as **PARTIAL** ("existing rows refresh in place every 10 s; newly started downloads appear on next load") or adding one sentence to UX-027 documenting that limitation.
- **N3 — UX-030 reload-path count.** UX-030 says "the four intentional `location.reload()` paths suppress the guard"; `settings.html` currently has **three** `location.reload()` calls (`1158, 1518, 1534`) plus one `window.location.href = '/'` reset redirect (`1489`). Say "three reloads + the reset redirect".
- **N4 — navigator anchors.** UX-027 says `href="#id"` but does not name the ids; only Diagnostics (`auto-download-diagnostics`), Inventory (`raw-downloads-card`), Failed (`failed-documents-card`), Staging (`staging-series-groups`) and Audit (`audit-rows`, a `<tbody>`) exist. Add the 8 anchor ids (e.g. `#dl-awaited`, `#dl-queue`, `#dl-cleanup`) and state that anchors point at section wrappers, not `<tbody>`.
- **N5 — pickup Refresh while dirty.** UX-028 blocks reload while dirty/focused but does not say what the "Pickups changed — Refresh" button does then. Define: it prompts to discard unsaved volume input (or saves on blur first); otherwise a dirty input can leave the stale banner unusable. (Auto-save on `change` makes the window small, but the path should be stated.)
- **N6 — UX-030 cross-reference.** It says the changed password semantics are "listed in §7"; §7 is the deferred table and has no password row — the deliberate change is listed in the §4 matrix (settings password blank/omit). Point at §4 or add a §7 note.
- **N7 — UX-014 vs showToast signature.** UX-014 keeps `showToast(message, type)` unchanged yet wants a Retry action on fetch-failure toasts. State the mechanism: a separate `showErrorToast(message, {retry})` (or optional third options argument) that composes the existing toast node — otherwise implementers will guess.
- **N8 — deferred dialog migrations.** UX-013 converts sheet/palette/lightbox/tag/feeds modals; §7 keeps "other modal migrations" deferred. The Downloads `#manual-match-modal`/`#staging-series-match-modal` and Manual Pickup `#pickup-match-modal` therefore keep current behaviour (no Escape/focus trap/scroll lock). That is an acceptable deferral with a stated reason, but it should be named in §7 (currently unnamed as a set) so the E-audit record is explicit.
- **N9 — nav markers.** §4 correctly demands `_desktop_nav`/`_mobile_menu` marker comments unchanged; the working tree's `base.html` rewrite keeps them — implementers must not reflow those comment anchors while making Downloads a dropdown.
